Presently, applying these transformations:
- raw int values are zigzagged, which doesnt add a lot of decompression time to un-zigzag, 
    and retains negative values to become small positive values. 
    so this should just always be done if there are any negative values
- time is converted into ns and differentiated twice!
    to keep the values small, 
    so they compress very well with bitpacking, 
    and to not do this, would add a lot of file size, it should be kept
    but, on decompression, double-cumsum adds a lot of time :(
        perhaps this would not be true if we create only one unified timeaxis?
    anyway, maybe this could be optimized somehow... if unified timeaxis has drawbacks
        does a prefix-sum with gaps (eg prefix-4) save time?
        highly likely a prefix-4 differential would give the same result as prefix-1
            on the second differential
        

- differentiating (& zigzagging) **random** values doesnt seem to help compression
    although i think it should be expected that with more "steady" values, it should help
    so we should have an option to check the differential, and the second differential, 
        and maybe compute some sum of how many small values 
        to judge if a differential could add extra bitpacking compression

- After properly implementing pfor & testing with ~100 MB uncompressed MDF file
    based on random integer data within i32 size
    looks like we do still get some meaningful compression:
    - 98 MB uncompressed MDF
    - 58 MB compressed MDF (using zlib compression, the ASAM standard)
    - 30 MB using MDFCompressor!
- Further, much faster to read (of course):
    - 12 seconds to read all messages from uncompressed MDF
    - 70 seconds (!) to read all messages from zlib-compressed MDF
    - 100 ms (!!) to read all messages from MDFDecompressor!
- Sort/diff random integers does not help, 
    because having to compress & include the order.
    ~1.2x larger including "sort-order & sorted/diff samples", vs just the random values as is
- compressing the compressed bytes does not help
    perhaps that should be expected... by someone smarter than me
